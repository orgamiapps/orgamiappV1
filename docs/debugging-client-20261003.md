## Confirmed defects and repairs

| Area | Original failure | Repair and regression coverage |
| --- | --- | --- |
| Guest authentication | Concurrent anonymous sign-in callers waited for an auth event that never arrived when the first request failed. | Share the same pending operation and outcome; clear it after completion so retry works. Existing full accounts are reused; late anonymous results use current Auth identity. |
| Guest persistence | Browser secure-storage failure made successful anonymous Auth look like failed sign-in; sign-out retained an old guest ID. | Auth remains authoritative when persistence fails; clear guest identity on sign-out. Anonymous users cannot be promoted by `disableGuestMode`. |
| Account identity | AuthService populated full-account profile state for anonymous users; an old customer object could remain during an account switch. | Full-account access requires a non-anonymous Auth user and matching customer UID. Change profile state synchronously on auth events; invalidate old cache and refresh the current identity. |
| Profile races | Delayed refresh, startup restoration, login completion and social-profile updates could restore an old account's profile after sign-out/switch. | Guard asynchronous results by current Auth identity and auth revision. Profile screen background refresh uses the guarded service. |
| Session storage | Concurrent save/clear operations could interleave IDs/email or clear a later account's stored session. | Serialize storage work and check current identity/revision at boundaries. Clear private in-memory data before asynchronous cleanup. |
| Profile integrity | Email login treated null/timed-out customer reads as absence, then overwrote the profile using plain `set`. Social creation could similarly overwrite existing fields after uncertain reads. | Email login keeps a local fallback without writing profiles. New social profiles use transaction create-if-absent and return any existing document. Signup remains responsible for creation. |
| Search availability | Public search required optional ONNX assets/native methods and SQLite before reaching its Firestore fallback. Missing web/native dependencies returned an empty result instead. | Route production event search through the existing shipped rule-based parser and public-event query. No model download, native plugin or SQLite is required. Location is optional, bounded and only checked for nearby queries. |
| Search races | Earlier async searches and enhancement responses could overwrite newer queries; clearing a query left pending work live; initial search was ignored after inventory arrived. | Version public/user searches, invalidate immediately on query changes and apply the current query after inventory loading. |
| Pagination | Public search used the last displayed, featured-sorted event timestamp as its page cursor, skipping equal-time records or repeating records after sort. | Keep the original Firestore document cursor and use `startAfterDocument`, then deduplicate appended IDs. |
| Private search | A legacy collection-group document-ID equality used a bare UID rather than a document path, causing the entire load to fail. Private results also survived account changes. | Query approved memberships by indexed `userId`; subscribe to auth changes, clear private results and reject late responses. Legacy memberships lacking `userId` require explicit normalization rather than an invalid broad fallback. |
| Error states | Public/private inventory failures rendered success-looking empty states. | Display retryable failures and restore results after a successful retry. |

## Follow-up: isolate public share links by environment

Root's staging qualification found that client sharing always produced `https://attendus.app`, while event/community URI parsers admitted only the production host. Fixed only `lib/Utils/app_constants.dart`, `lib/Services/event_share_service.dart`, and `lib/Services/community_share_service.dart`, with focused tests:

- Canonical origin follows the existing `ATTENDUS_FIREBASE_ENV` selector: production remains `https://attendus.app`; staging uses `https://attendus-staging.web.app`; debug emulator defaults to `http://127.0.0.1:4173`.
- The staging parser also accepts its same-project `attendus-staging.firebaseapp.com` Hosting alias. Production, staging and emulator absolute record URLs cannot be resolved in another environment even if document IDs match. Relative application routes remain scoped to the running environment.
