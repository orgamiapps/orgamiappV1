# Web release pipeline — 2026-10-04

This change separates **implemented release safeguards** from **deployed or qualified evidence**. Writing these workflows and passing their local tests does not qualify a release. No workflow was dispatched and no cloud deployment was performed by the platform implementation agent.

The user authorized web qualification and eventual deployment after the required staging acceptance, including the 24-hour pilot. Native store signing, installation and physical-device acceptance remain separate. The existing native release workflow and full-project quality workflow remain available.

## Release sequence

1. Commit and review one candidate revision on the approved candidate branch or `main`. `web-ci.yml` runs the web-only quality workflow on PRs and pushes to `main`/`codex/**`; the required completion check is `web-quality / quality-complete` (the actual hosted GitHub job name was verified on 2026-10-04). Existing full/native CI remains separate. For initial bootstrap, push the reviewed branch, pass web CI, and merge the new dispatch workflows onto the default branch before dispatching them. Select that exact committed revision for each release workflow. The candidate must be clean; changing any source, workflow, test producer or deployment configuration requires a new candidate.
2. Run **Freeze web candidates and deploy staging** (`firebase-release.yml`). It runs the web quality workflow once, captures both live predecessor deployment states and the exact prior staging Hosting files, then builds staging and production separately from the same source SHA. Each environment is built once. The immutable artifacts are `web-candidate-staging`, `web-candidate-production`, `web-staging-predecessor`, and `web-predecessors`.
3. The same candidate workflow deploys **only staging**. It rechecks the staging predecessor before any write and publishes the verified additive public asset bridge described below. It then deploys explicit Firestore rules, indexes, Storage rules and named Functions; waits for index/TTL readiness; checks default database and Storage rules and the two analytics trigger contracts; rehearses the four representative backend source rollbacks and candidate restorations described below before fixtures exist; then publishes the retained staging web bytes. Both staging domains are verified against the packaged file hashes. The `web-staging-deployment` artifact contains the intermediate Hosting and backend operation receipts and binds the final observed deployment state to the restored candidate.
4. Run **Collect executable staging web evidence** (`web-release-observe.yml`) on the same source revision. Choose the browser, backend, operations or Safari producer. Safari selects a pinned `macos-15` hosted runner; the other producers use Linux. `gates=observation` applies to backend/operations and permits early health observations without pretending the 24-hour close/replay gate has passed. The browser-only `gates=post-close-replay` mode runs the isolated reconnect/replay probe described below. Unsupported producer/mode combinations fail before cloud authentication. Supply prior successful evidence run IDs when comparing history. The wrapper downloads and validates those immutable artifacts before exposing their reports to a producer.
5. Begin observations within 20 minutes of the staging deployment. Collect at least hourly; gaps over 75 minutes invalidate continuity. Complete the full browser and Safari journeys while the controlled event remains open, and retain their successful immutable evidence run IDs. Any full browser retry must also finish before the event closes; its registration journey cannot legitimately pass after closure. Once the actual effective check-in window closes (the fixture currently uses a 60-minute grace after event end), run `producer=browser`, `gates=post-close-replay` with the original successful browser run ID. Retain its successful auxiliary replay report. Continue observations for at least 24 hours, including 24 hours after the actual controlled event closes. After that interval, collect final full backend and operations evidence, supplying both original browser and replay run IDs along with the observation history. Reuse the validated same-candidate browser/Safari reports from before closure. Do not change the event schedule, create a replacement pilot, or fabricate successful registration to work around a missed pre-close gate. Elapsed time alone is insufficient.
6. Run **Qualify the observed staging web candidate** (`web-release-qualify.yml`), passing the candidate run ID and the comma-separated evidence run IDs. Every gate must have executable assertions and retained raw output, no active journey blocker, the same source/configuration/web/backend/rules/index identities, an unchanged live staging deployment, and a fresh final observation. It produces `web-qualification` only after all checks pass.
7. Run **Promote the exact qualified production web artifact** (`web-release-promote.yml`) with that successful qualification run ID and the exact captured prior production Hosting version resource. It downloads the production artifact from the original candidate run, rechecks its GitHub provenance and byte hashes, rechecks staging and the complete prior production deployment state, and uses the same verified asset bridge before deploying Functions and the exact web artifact without rebuilding. Both production domains are verified. The promotion receipt, intermediate Hosting receipt and curated deployment output are retained as `web-production-promotion`, including when deployment fails.

There is no production promotion on a main-branch push. The former standalone Functions and index deployment workflows fail with instructions to use the qualified sequence. PR workflows have no production Hosting deployment credentials. No workflow uses broad `functions` selection with `--force`.

## Required evidence

All of these gate IDs are required:

- `browser-auth-guest-organizer`
- `account-switch-privacy`
- `cache-upgrade-deeplinks`
- `accessibility-responsive`
- `data-migration-recovery`
- `owned-staging-pilot`
- `event-close-replay-observation`
- `rules-storage-indexes-TTL`
- `backend-trigger-canaries`
- `rollback-rehearsal`
- `notification-delivery-isolation`
- `large-roster-export-download-expiry`
- `safari-web-acceptance`

The collector invokes only the frozen `tools/web_release_producers/browser.js`, `backend.js`, `operations.js`, or `safari.js`. A producer returns actual assertion values, expected values and raw output paths. The wrapper performs the comparisons, computes SHA-256 hashes, records trusted runner start/end times, reads deployment state independently, and binds reports to its workflow run. It does not accept a user-entered `passed` flag.

The browser producer groups its related gates into one real browser run. The prior/current cache test receives both verified artifact trees, rather than arbitrary fixture paths or a synthetic cache. The backend producer records provider-capture isolation, analytics trigger behavior, live recovery comparisons and replay observations. The operations producer records the owned pilot, deployment/TTL health, independently rereads the completed backend rollback/restoration operations, and rehearses Hosting rollback on a dedicated expiring staging preview channel. The Hosting preview does not replace the live channel and cannot qualify the rollback gate by itself.

The auxiliary `post-close-replay` report does not replace any of the 13 required gates. The original pre-close pilot retains exact synthetic registration, admission and export request envelopes and safe response IDs. It retains only the announcement request digest; a guarded private observer resolves and verifies the original permission-bound preview/job ID. Passwords, ID/App Check tokens, management links and signed download URLs never enter these receipts. The replay-only browser starts fresh real UI login sessions, verifies App Check, sends each original request using browser-page `fetch` while offline, then reconnects and issues exactly that request again. It expects the original registration/announcement/export receipt, while manual check-in after its effective close must be rejected by the existing closed-window contract. Canonical event, admission, job, attempt, capture and roster snapshots must remain unchanged. This is reconnect testing of known completed requests, not a delayed new attendance submission.

Export replay additionally requires its original completed job and generation to remain live and at least five minutes from expiry. An expired original export is explicitly omitted using its immutable completion/expiry proof; a missing unexpired job blocks the probe. No new export key or replacement job is submitted. Operations separately verifies expired object removal. The final backend gate requires the provenance-verified actual replay receipt linked to its original pilot report and checks the current schedule/policy; passive terminal-job observations alone cannot satisfy it. The final qualification contract also requires that exact auxiliary report, while preserving the existing 24-hour observation and freshness requirements.

Only successful first-attempt manual runs of the allowlisted workflows in `orgamiapps/orgamiappV1`, from the exact candidate SHA, are accepted. A rerun with the same run ID is not accepted: start a fresh manual run. Artifact IDs, archive digests and report digests are retained in the qualification receipt. Missing, expired, failed, cancelled, fork-origin or changed artifacts are rejected. Qualification expires after 24 hours; promotion also requires the staged deployment to remain unchanged.

The evidence upload is curated from the reports' declared files. Firebase debug logs, environment files, credential files, private-named files and undeclared outputs are excluded. Function environment values are represented only by a digest in deployment state. Private source records and recovery bundles stay in private storage; reports contain bounded fixture observations and comparison evidence.

Blocked assertions and incomplete observation gates are retained under `diagnostics/` together with safe raw files and their hashes. The artifact index distinguishes passing reports from diagnostics, and a blocked collection exits unsuccessfully. Qualification still rejects a failed workflow's provenance; retaining a useful failure never promotes it to accepted evidence. An observation-only run can succeed independently while a full 24-hour gate remains pending.

## Actual desktop Safari acceptance

The read-only feasibility review found that GitHub's [macOS runner image](https://github.com/actions/runner-images/blob/main/images/macos/macos-15-arm64-Readme.md) includes branded Safari and its driver. Apple supports enabling the installed driver with [`safaridriver --enable`](https://developer.apple.com/documentation/safari-developer-tools/macos-enabling-webdriver), and permits [one isolated automation session at a time](https://developer.apple.com/documentation/safari-developer-tools/webdriver). Playwright explicitly [does not drive branded Safari](https://playwright.dev/docs/browsers#webkit); passing its WebKit suite is separate evidence.

The Safari producer uses the installed `/usr/bin/safaridriver` through bounded loopback W3C WebDriver requests, with no new package dependency and one session. It records actual returned browser name/version/platform, `sw_vers` output, driver version, runner image metadata, and candidate/fixture provenance. A WebKit/Chrome capability response, non-macOS execution, mismatched live artifact, or unbound fixture cannot pass.

The implemented journey validates the real public guest form without submitting a registration; retained owner UI login and management access; sign-out and account switching; private-route denial; public and Flutter history/reload; a narrow desktop viewport with 200% HTML text; and an actual downloaded calendar file bound to the owned event. The real Safari window's returned inner width is recorded because browser chrome can impose a minimum window width. Screenshots avoid password inputs; browser credentials remain in memory. Normal anonymous identities created by public/app login are recorded as raw UIDs with project/run provenance for exact scoped reconciliation, and are retained without deletion. No provider send, account deletion or event mutation is part of this producer.

This is implemented coverage, not a successful Safari run. Actual runner startup, Safari rendering/semantics, App Check and download permission behavior must execute and pass. iOS Safari, physical-device notification permissions and installed web-app delivery remain outside this desktop gate. The existing 24-hour observation span, post-close interval and 75-minute maximum observation gap are unchanged.

## Frozen manifests and drift

`candidate.json` contains the source Git SHA, candidate run, environment/project, immutable release ID, SHA-256 maps of tracked source and web files, configuration digest, deployment manifest and captured predecessor states. The deployment manifest includes explicit function names, an empty deletion list, backend source digest, Firestore/Storage rule digests, index manifest digest and Firebase configuration digest.

Tracked source hashes use exact committed Git blob bytes, so Windows checkout line endings and Linux checkout line endings bind to the same source. Actual tracked edits are rejected. Backend deployment materializes only that committed `functions/` tree into an isolated directory, restores locked dependencies there, and verifies the source again. Untracked local files cannot enter a Functions upload. Web artifacts retain their exact packaged byte hashes; they are never normalized or rebuilt during promotion.

Live deployment state records Hosting version/release identity, complete ServingConfig and file inventory hashes, allowlisted Functions metadata, Gen1 source archive/version references, Gen2 immutable source bucket/object/generation and build references, Cloud Run revision/container image metadata, rule releases/ruleset source hashes, and indexes/field overrides including TTL. Image digests and source generations that the API does not expose remain explicitly unavailable; they are not invented. Source archives and container environment values are not uploaded. The exact default Firestore Rules release is `cloud.firestore`. Named database rule releases are captured for drift detection and preserved; default-database rule verification does not silently overwrite them.

The public renderer uses physical `/public-web/v1/assets/<raw-sha256>/<filename>` paths. Before any new renderer can execute, `bridge_web_assets.js` clones the exact captured predecessor version into a mutable `CREATED` version, independently verifies every old file hash and the full ServingConfig, and adds only missing immutable asset paths from the sealed candidate. Every predecessor immutable path must already exist with its correct raw hash in that candidate, or sealing fails. Original Flutter files, legacy asset paths, headers and rewrites remain identical in the bridge. No bytes are added to the sealed candidate during deployment.

The bridge distinguishes raw asset SHA-256 from the SHA-256 of the gzip-9 upload bytes required by Hosting. It finalizes and rereads the union of predecessor files plus new assets, checks that the predecessor is still live, releases the bridge, and verifies actual raw asset bytes on both environment origins. The pipeline verifies the recorded intermediate Hosting identity before Functions and immediately before the final candidate Hosting release, which retains the prior immutable paths. Official API contracts: [clone with `finalize:false`](https://firebase.google.com/docs/reference/hosting/rest/v1beta1/sites.versions/clone) and [populate only new paths using compressed content hashes](https://firebase.google.com/docs/reference/hosting/rest/v1beta1/sites.versions/populateFiles).

`hosting-asset-bridge.json` records the candidate/source, captured predecessor, clone operation, additive manifest, intended transitions, published version/release and HTTP evidence. Mutation intent is saved before each API call; requests do not automatically retry. Missing acknowledgements, drift, wrong live bytes or a prior partial receipt stop deployment. Preserve that receipt and inspect actual live state before preparing a new candidate; there is no automatic resume, rollback or overwrite of uncertain releases. Local fault-injection tests and read-only API inventory checks are preparation evidence only. A successful live bridge still requires execution within the authorized staged release sequence.

The index verifier now rejects unexpected field indexes and unexpected active TTL policies in addition to missing, creating, terminal or extra composites. It requires expected TTL policies to reach `ACTIVE`. Noninteractive deploys have no forced deletion switch: an incompatible deletion requirement is a blocked release that needs a separate explicit reviewed operation.

`triggerAIInsights` retains `google.cloud.firestore.document.v1.updated`; `triggerAIInsightsV2` adds `google.cloud.firestore.document.v1.written`. Both target `event_analytics/{docId}` in `us-central1`, share the deduplicating source-fingerprint handler, and remain exported during overlap. Neither deployment nor promotion retires the old trigger. Retirement requires a separate named operation after create/update/delete, overlap/retry and observation evidence with rollback metadata retained.

## Recovery boundary

The only supported real restore target is `attendus-recovery-20261004`, never production or staging. `functions/tools/recovery-target.js` checks fresh project metadata and labels, exact deny-all rule source, and complete listener inventories. Where a listener API is disabled, it requires a complete project-scoped Service Usage inventory and current IAM/custom-role definitions; a generic permission denial is not proof of absence. Unapproved service creators, inherited policy that has not been inventoried, mutating custom permissions, active listeners, stale evidence and permissive rules fail validation.

`tools/capture_recovery_target.js` obtains this proof through read-only APIs without enabling services. The dedicated target proof must be refreshed before recovery verification. An export/import success response is only one input: the migration/recovery producer also checks source/archive fingerprints and restored content. Any unresolved data ambiguity remains a release blocker.

## Representative backend rollback

`config/web_backend_predecessor_archives.json` retains the original and private backup bucket/object/generation plus actual archive SHA-256 for every captured predecessor function. These immutable backups must exist before candidate Functions deployment. The current manifest records 152 staging and 135 production archives; production archives are retained for recovery and are never deployed by the staging rehearsal.

`tools/rehearse_web_backend.js` is restricted to the current staging candidate workflow and refuses production. Before and between changes it verifies the specified business, notification and qualification collections are empty and Auth has no identified account (at most the single existing anonymous account). It selects exactly `publicWeb` (HTTP), `getOrganizerEventRegistrationsV1` (callable), `aggregateAdminMetricsDaily` (scheduled), and `triggerAIInsights` (Firestore updated). Missing or incompatible predecessors stop the operation.

For each representative it verifies the old private archive bytes, retains a write-once private copy of the just-deployed candidate source, and patches only `buildConfig.source` to the pinned old archive. It waits for the actual Google operation to complete, verifies the live source generation and unchanged runtime, entrypoint, service and trigger configuration, then restores the retained candidate source. Restoration runs after every attempted rollback, including failures. A restoration failure stops subsequent work and leaves its recovery metadata in the failed receipt; it never produces a successful deployment receipt.

The final verifier independently rereads all eight operation resources and current function metadata, checks their ordering, source generations and configuration digests, and rehashes the retained candidate archives. The gate receipt names this representative scope explicitly. It demonstrates four source rollback/restoration paths, not a full-fleet rollback or production recovery exercise. All exports remain present and no function deletion occurs.

The staging deployer needs Auth read permission, read access to its current source bucket, private staging-source prefix reads, and create-only access to `backend-source/attendus-staging/candidates/`. Runtime/build service agents need the matching private staging-source read prefix. These grants do not include production backup records or overwrite/delete permission. IAM provisioning and live execution are owned by the root operator.

## Local script

Normal `scripts/build_web_release.ps1` execution is build-only and enforces the lockfile. A local or dirty build is not a qualified deployment artifact. `-Deploy` requires `-Environment production`, `-QualificationRunId <successful run ID>` and `-ExpectedPriorRelease sites/orgami-66nxok/versions/<version>`. That branch returns into the same provenance-verifying promotion tool before Flutter, dependency restoration or key lookup. The tool downloads the frozen artifact; it never rebuilds or accepts a local replacement.
