### Push-token account handoff

A subsequent shared-device review found that the client only wrote the current user's `fcmToken`; it could not atomically clear a previous user's ownership after Firebase Auth had switched accounts. Backend and client workstreams therefore added a coordinated ownership protocol before final qualification:

- `registerPushTokenV1` and `revokePushTokenV1` accept `{token, expectedUid, installationId, generation}`. The full authenticated UID must match `expectedUid`. Installation UUID and positive safe-integer generation are persisted by the client before each registration/revocation intent. Older generations cannot reverse a newer account's intent; identical same-generation registration only replays while its binding remains current.
- Private `PushTokenBindings/{sha256(token)}` uniquely binds a token to its owner, installation hash and generation. `PushInstallations/{sha256(installationId)}` fences out-of-order operations. Registration atomically updates the current user and removes the previous user's token only when that field still identifies the transferred device. Rebinding through a new installation invalidates late operations from the previous installation, returning the stable `installation-reset-required` code for client token rotation.
- An old account's revoke never removes a rebound owner's token or advances the new owner's generation. Direct client token writes and registry reads/writes are denied. `canDeliverPush` checks the user field, active token binding, matching installation owner/generation and account-deletion guard. Legacy unregistered tokens fail closed until the updated client registers; rollout must coordinate clients, callables, sender guards and rules.
- Deletion cleanup rereads each token/installation owner inside its lease-fenced transaction, preserving any binding transferred after its selection query. Final inventory checks both collections. Registry records use token/installation hashes and do not store the raw token; the authoritative user field remains private.
- Parent integrated the common delivery guard into messaging, reminders, discovery, administrator dispatch and pending pushes. The legacy sender in this workstream uses the guard at reservation and immediately before handoff and includes `recipientUid` in the push envelope. Client workstream owns auth-epoch fencing, bounded revoke/logout, persisted pending work and account-aware notification handling.

Focused push-token plus notification run: **10/10 passed**, with scoped lint clean. Tests cover atomic account transfer, late old revoke, rotated-token/generation conflicts, invalidated prior installation, anonymous/current-account/deletion checks, legacy-token suppression, and deletion/query handoff races. A real-Firestore ownership-transfer case was added to the community emulator suite, plus direct-write/read denial rules coverage. No real FCM send occurred; provider behavior and signed-device acceptance remain separate.

Deletion's new group-upload cleanup is deliberately constrained to groups proven by indexed membership/content references, with those scopes checkpointed. It does not claim discovery of historical orphan uploads whose membership and post records were already removed. ## Final customer-profile trust follow-up

The parent's final rules review identified another concrete entitlement defect: a newly created `Customers/{uid}` document could inject a negative `eventsCreated`, and an existing owner could lower, reset or remove that field. `events/wizard.js` used the client-writable number to enforce the five-event free publication allowance. Administrator authority was independently checked through verified custom claims and private `admin_roles`; injected customer `role`/`isAdmin` fields were not demonstrated to grant administrator access. Paid publication tiers come from private `subscriptions`, and unlimited event creation comes from private `account_entitlements`.

Rules now reject reserved privilege/entitlement fields on customer creation, accept only omitted or integer-zero `eventsCreated`/`groupsCreated` signup defaults, and prohibit changes/removal of `eventsCreated` after creation. The private `users` profile also rejects its existing reserved update fields on creation. Normal and social signup both serialize `CustomerModel` with the two zero counters, so their full field shape remains accepted. Personal profile updates remain permitted. A legacy client-side `Customer` to `Customers` migration with nonzero counters is deliberately not trusted to establish server allowances; such data needs an authorized server migration rather than resetting the counter.

The publication callable now rejects omitted, negative, fractional, string, null, boolean, non-finite and unsafe-integer historical counters with `failed-precondition`, with no writes. An existing organizer without a counter requires reconciliation; the implementation does not invent a fresh allowance or infer a lifetime total from currently retained Events. New authenticated signup and new server-created guest-upgrade profiles explicitly initialize zero. This does not establish that historically reset but otherwise valid nonnegative counters reflect all prior creations; no cloud reconstruction was performed. Explicit trusted unlimited/premium entitlements retain their intended behavior.

The same review reproduced a stale-snapshot quota race: the profile identity was fetched before the publication transaction, so concurrent drafts could reuse the same old count. Publication now rereads the current customer counter transactionally. It also rereads the authoritative subscription and aborts if the preflight tier changed, before any event/quota write. The preflight and transaction use the same tier parser, preserving existing active/cancel-at-period-end and legacy active-flag semantics instead of inventing a new billing grace policy. A real-Firestore regression covers the final available slot under concurrent requests, missing counter rejection and stale premium-tier rejection.

Added rules regressions cover reserved create fields, negative/invalid counters, the complete signup profile, minimal legacy-compatible creation, ordinary personal edits and prohibited quota reset/replacement. Unit regressions cover malformed stored counters, the final permitted increment, stale profile snapshots and tier changes. The frontend confirmed the old `create_event_screen.dart` immediately delegates to the active event-creation gate, so its direct quota increment path is unreachable. Both active profile editors now omit server counters to avoid overwriting a newer publication count with stale UI state. This workstream started no emulator; the parent owns serialized validation.

## Final cross-account profile privacy correction

The former `Customers/{uid}` read rule allowed every full account to fetch or list every raw profile. This exposed email, phone, age/gender, favorites and any extra stored fields, including profiles excluded from search. Active search fallback code could download the entire collection before filtering locally. No existing general public projection prevented this disclosure.

The coordinated server and client correction is now local and ready for deployment qualification:

- `getPublicProfilesV1` accepts at most 50 known IDs and returns only `uid`, `name`, `username`, `profilePictureUrl`, `bannerUrl`, `bio` and `isDiscoverable`. Images must use safe HTTPS URLs; nested/private metadata cannot enter the DTO. Deleted/deleting profiles are omitted. Known-ID cards remain available to existing chats/groups even when discoverability is disabled; that preference controls search inclusion. Valid imported Firebase UIDs retain punctuation while path separators/control characters are rejected.
- `searchPublicProfilesV1` supports bounded name/username prefixes and limits 1–50. Explicit discoverability is filtered in each database query before the limit, then reread with current deletion/privacy state before response. Two explicit Customers composite indexes support those queries. This is not exhaustive arbitrary-substring/full-text search. No unbounded collection fallback remains in the migrated clients, and the endpoint rejects email lookup.
- `checkUsernameAvailabilityV1` provides a trim/lowercase normalized boolean result, excluding the caller's own UID from conflicts and returning no matching profile. It is an advisory check against normalized stored usernames, not an atomic reservation or a historical mixed-case uniqueness migration.
- `lookupEventStaffAccountV1` requires an attested full account with current event-management authority and an exact valid email. Its ten-per-minute limiter precedes Firebase Auth lookup; editable `Customers.email` cannot redirect identity. It only returns a minimal public card for a verified, enabled, non-anonymous account with an available profile. Missing/unverified/disabled/deleting targets return the same null result. Current event role and actor/target deletion are rechecked after the Auth call. Known-UID staff grants keep their existing separate contract.
- `ProfileReadLimits/{uid}` is private, bounded per operation, protected by transactional account-deletion guards, included in leased root cleanup/final inventory, and has declared expiry TTL metadata. The cloud TTL/index changes have not been applied by this workstream.
- The frontend migrated active public profile/card/search/username, route restoration, group member/admin, blocked-user, messaging and staff lookup paths before the raw profile rule was changed to self-only. Public profile UI inspection confirmed that profession/company/location/website/social fields are not displayed cross-account; no visible public field was silently removed. Self profile/auth/signup/preferences/quota reads remain direct. Older clients relying on raw cross-account reads fail closed and require an update. No rule fallback preserves the disclosure.

The rules follow-up also changed `canReadEvent`'s missing `private` default from false to null: legacy events lacking that flag no longer reveal child comments to unrelated users when the parent itself is not public. Explicitly authorized owners/invitees remain covered by the new fixture.
