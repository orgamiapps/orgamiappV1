# Secure live quiz repair — 2026-10-03

The exposed quiz UI previously used direct Firestore reads and client-calculated scores while the rules denied every quiz collection. The replacement uses `quizMutationV1` and `quizReadV1`, created by `functions/quiz/service.js`. This is local source work; deployment and installed-device acceptance remain separate.

## Contract and authority

- Mutation input: `{action, quizId?, eventId?, questionId?, participantId?, requestId?, expectedRevision?, payload}`. Host mutations require a stable request ID; lifecycle actions require the last observed revision. The same identity and canonical payload replay the recorded result, and mismatches are rejected. The caller's current event-management authority is checked even on retries.
- Host actions: create, update, delete, addQuestion, updateQuestion, deleteQuestion, reorderQuestions, start, pause, resume, next, end, restart. Question/settings changes require a draft. Restart requires an ended run and advances the session. Delete creates a tombstone and removes the event's quiz pointer; historical records are retained for disposition, not silently destroyed.
- Participant actions: join, leave, submitAnswer. Authenticated anonymous sessions can join only when both event access and quiz policy permit it. Participant IDs are bound to the authenticated UID and quiz. Participation and capacity changes are transactional and idempotent. Capacity is a bounded per-run enrollment limit (maximum 1,000), not unlimited turnover through leave/rejoin.
- Answer input: top-level question/participant IDs and `{answer, session}`. The server rejects stale sessions, closed questions, inactive participants and conflicting second answers. It ignores caller time, score, correctness and question index. Exact-answer grading and speed bonuses use server time; pause duration is excluded. A deterministic response ID makes concurrent retries award points only once.
- Read actions: quiz, getByEvent, questions, currentQuestion, participant, participants, questionResponses, participantResponse, stats. Every read rechecks event access. Participant reads default to the caller; detailed answers/statistics require host authority except a participant's own response. Missing quiz IDs resolve through the protected participant or question lookup when old client signatures supply only those IDs.
- Read envelopes contain `{data, serverTime}` with millisecond dates. Questions include their quiz ID and session from the same transaction. Non-host question reads omit correct options, acceptable answers and explanations. Future questions are hidden. While a question is open or paused, own response scoring keys are omitted and `gradingPending` is true; leaderboard/self totals also omit that question's contribution. Closed responses include server base points, bonus and total points. Leaderboards omit UIDs and honor the show-leaderboard setting.
- Auto-advance is evaluated from server deadlines when the quiz is read or mutated. It does not depend on a client timer and can catch up through multiple elapsed questions. No scheduler is needed; an unattended quiz's persisted status catches up on its next authorized interaction.

## Storage and deletion

All direct client access remains denied. `LiveQuizzes` holds state; `LiveQuizSecrets/{quizId}` holds the private question array with an `operations` subcollection for host retry markers. `LiveQuizQuestionLookup/{questionId}` contains only quiz ID. `QuizParticipants` and `QuizResponses` hold UID-bound membership and answer records. Legacy quiz layouts fail closed with an organizer-recovery message rather than exposing old answers or accepting client scores.

`quiz/account-deletion.js` removes a subject's responses and participants under the existing deletion-worker lease, updating current-run aggregate and membership counts. It also removes legacy responses linked only by participant ID before deleting that durable owner link, so interruption retries retain provenance. Conflicting response ownership stops for review. Other participants and organizer content survive. Organizer ownership (`LiveQuizzes.creatorId`) and host marker retention (`operations.actorUid`) require explicit review in the shared account-disposition registry; backend workstream owns that integration.

## Evidence and limits

- `functions/test/live-quiz.test.js`: **17/17 unit cases passed**, including defensive ownership-conflict review. The in-memory transaction fixture buffers writes and rejects reads after writes. Coverage includes concurrent retries, score forgery, private/anonymous/host boundaries, redaction, server deadlines, pause/resume, revision fencing, restarts, capacity cycling, deletion idempotency and lost deletion leases. The parent ledger owns the combined Node 22 run; this focused local run used the available Node runtime.
- `functions/test/live-quiz-emulator.test.js`: five real-Firestore/rules cases are prepared for the parent's serialized local demo emulator run. This workstream did not start an emulator. The suite covers actual concurrent transactions, authorization and deletion guards, deadline/session behavior, subject-only cleanup, and direct read/write denial for all quiz collections and private descendants.
- Targeted ESLint passed for the module and both test files. Initial unit evidence included one test setup error (host response lookup defaulted to the host instead of the player); the explicit participant ID fixed the test and all 16 passed.
- Deployment must include the two callables and matching client/rules changes. Existing legacy quizzes need inventory and an explicit recovery/migration decision. Real host/guest, reconnect, multi-device latency, App Check, installed native behavior and sustained high-attendance load are not established by local unit tests or a compile-only artifact.

Paid activation, refunds, biometrics and Wallet issuer delivery remain unchanged and disabled as previously scoped.
